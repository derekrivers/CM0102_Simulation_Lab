# Manager-bound ordinary-club plan selection and bank lookup

This evidence extends the synthetic null-manager boundary of PC-R3 to three
actual ordinary clubs with nonnull manager records and actual tactical banks
from a retained private runtime capture. It qualifies a connected setter,
row resolver and bank getter. Human manager registry state, original UI actions,
match application and original saved games remain unqualified.

## Corrected field meaning and state admission

The prior phrase "club owner pointer at +0xcf" was too broad. Original loader
instructions `00531dad..00531e0f` read club `+0xcf` as a signed staff-table index:
valid `0 <= index < staff_count` becomes `staff_base + 110*index`; negative
indices become null, and high indices take a diagnostic branch before nulling.
This is a static, locally verified fixup contract, not execution qualification
of the complete database loader. The captured records already contain pointers
and require no speculative relocation.

Original classifier `00600a50` checks this same nonnull pointer, reads the staff
record's ID, and compares it signed against global staff count minus sixteen.
The manager role is supported by the loader's staff target, staff identity,
manager-specific classifier and downstream human-manager dependencies. It is
not club ownership or chairman identity.

The selected actual records satisfy all of these checked conditions:

- Club pointer is a full 581-byte row in the captured club table; its ID equals
  the row index and is below `club_count - nation_count`.
- Manager pointer is nonnull, within the captured staff table, aligned to its
  110-byte stride; its ID equals its row index and is below `staff_count - 16`.
- Mapping stride is `0x91`; its first signed word is inside the combined bank
  count. Both complete bank extents and the complete club/staff/mapping tables
  lie within captured memory.
- Captured counts are 2,514 clubs, 213 nations, 9,520 staff and tactical banks of
  17 and 28 entries. Each tactical entry occupies 6,371 bytes.

This nonhuman manager branch falls through `005409b0` and returns zero. All
three records are ordinary clubs, so national-team recursion is not admitted.
The captured context, club, staff, mapping and plan bytes are real inputs;
only the emulator stack, stop address and test command sequence are synthetic.

## Connected original effects and Rust boundary

For each selected club, original `008967d0` accepts the signed low word of the
plan argument, calls original row resolver `008982b0`, writes exactly two bytes
to that club's mapping selection word, returns EAX 1 and pops twelve argument
bytes. Repeating the same selection still writes the word. The resolver returns
the club ID and writes no non-stack state. Options 0, 1 and `0xffffffff` all
follow the same supported branch for these actual manager records.

Original getter `00896660` reads that updated signed word. For selection `k`,
first count `f` and stride 6,371, the normalized result is:

- `k < f`: first bank, entry `k`, byte offset `k * 6371`.
- `k >= f`: second bank, entry `k - f`, byte offset `(k - f) * 6371`.

The getter makes no non-stack writes on this admitted branch and pops eight
argument bytes. It does not read or interpret the plan bytes. The oracle checks
that the returned pointer identifies the exact captured entry and that its
bytes remain unchanged. This permits Rust's `PlanLocation { bank, index,
byte_offset }` projection without exposing original native pointers or claiming
that plan contents are implemented. The three routines execute as connected
API invocations, not as their entire match-setup caller.

## Results and limits

[The public original-execution corpus](evidence/manager-bound-plan-oracle-v1.json)
contains 21 connected cases: each of three actual manager-bound clubs exercises
its captured selection, first-bank zero/last entries, second-bank first/last
entries, repeated selection and the original ignored upper argument word.
The 63 successful calls cover 153 distinct original instruction starts. Every
instruction and non-stack data read is admitted; no callee is stubbed. Ordered
writes, return values and stack cleanup match. The complete 108,564,672-byte
heap is unchanged except the three admitted selection words.

Six deliberately wrong transition models are checked against observed outputs:
wrong row, dword store, omitted store, extra registry write, wrong bank and
wrong stride. The first five differ in all 21 cases; wrong stride differs in
six cases because zero-offset entries cannot distinguish a stride.

Nine structural host guards reject malformed club/manager references,
national-club IDs, human-reserved IDs and invalid selections. These are host
admission tests, not equivalent original error handling. Three additional
original-instruction probes are retained as **censored, unsupported** runs:
negative and limit plan IDs reach diagnostics, while a human-reserved manager
ID reaches unqualified classification helper `0053b900`. They make no non-stack
writes before the boundary. Including these probes yields 165 instruction
starts; their status is separate from successful entry-to-return cases.

The real registry path remains separate: getter `00896660` can call `005fbe20`
and `005fbd00`, selecting through a registry byte at record `+0x9a69`. That
lookup can mutate state. Neither its lifecycle nor original human control has
been qualified here. Null-manager, malformed selection, diagnostics, national
teams, human-reserved staff and non-admitted reads cannot silently enter the
new supported profile. Public fictional regression inputs must remain labeled
synthetic and separate from this real private-state receipt.

## Reproduce

Using Python 3.12 and Unicorn 2.1.4 in the private research environment:

```sh
python3 scripts/qualify_manager_bound_plan.py \
  /private/official/cm0102.exe \
  /private/retained-capture/snapshot \
  /tmp/new-manager-bound-oracle.json
```

Outputs use exclusive creation. The input hashes and emulator version are
mandatory; any unsupported instruction, state read, write, return, stack
cleanup or sentinel change fails execution. A rerun's output must exactly match
the retained public receipt, rather than replacing it automatically.


## Implemented management boundary

Delivery [PR #33](https://github.com/derekrivers/CM0102_Simulation_Lab/pull/33)
adds the private capture projection and a separate public fictional regression
fixture to `cm-management`. Rust accepts only their reviewed canonical SHA-256
fingerprints, in addition to explicit record/count/name/domain validation. An
arbitrary record, spoofed origin, reserved human-manager ID, national-club ID or
changed captured selection cannot enter the profile by declaring itself valid.
The accepted private fixture stays outside Git and build output. A loopback-only
preview may serve it on explicit request; React imports it through Rust.

Club IDs are sparse stable identifiers. Selecting a club changes the view;
`SelectPlan` changes only its mapping selection and emits the existing ordered
Rust event. `PlanLocation {bank,index,byte_offset}` is calculated by Rust from
the qualified getter contract. Manager links are immutable reference context,
not a newly implemented appointment command. Plan names remain fictional and
squad records are absent from this capture projection. The interface says so.

Version-2 slice saves embed the admitted fixture, profile, state, event log and
command deduplication. Load validates the fixture again, reconstructs the
initial world and replays every accepted command before replacing state. The
version-1 save schema and fixture remain unchanged, including byte-identical
re-export of a retained fictional version-1 save. No implicit migration or
original-save compatibility is asserted.

[The browser receipt](evidence/pc-r3-manager-browser-v1.json) records 105 operations:
37 legacy cases, 34 public synthetic-manager cases and 34 real captured-manager
cases. Each profile compares full native/browser state, events, save data and
